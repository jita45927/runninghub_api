# 系统性 BUG 与安全风险修复报告计划

本任务只交付问题证据、影响、根因、修复建议和验证方法，不修改业务代码，不在报告中提供可直接替换的补丁，不提交 Git，不重新构建安装包。

## Current State Analysis

已确认的架构与信任边界：

1. **本地服务入口**：[server.py](file:///d:/project/runninghub_api/server.py)
   - 绑定 `127.0.0.1`，同时提供静态文件和本地操作接口。
   - `/save-tool`、`/delete-tool`、`/save-cover`、`/rename-cover`、`/save-image` 会写文件或下载远程内容。
   - `/open-dir`、`/pick-download-dir`、`/open-url`、`/shutdown` 会调用系统能力或改变进程状态。
   - 文件路径由 `appinfo.txt`、HTTP 参数及程序目录回退逻辑共同决定。
2. **桌面进程入口**：[launcher.py](file:///d:/project/runninghub_api/launcher.py)
   - 负责后台服务启动、端口选择、单实例、托盘、浏览器应用窗口及退出确认。
   - 窗口、托盘、后台服务三者生命周期不同，需要核对异常路径和重复启动行为。
3. **远程 API 边界**：[api.js](file:///d:/project/runninghub_api/js/api.js)
   - API Key 从 `localStorage` 读取，并通过请求头发送；节点信息接口还拼接了查询参数。
   - API 根地址可配置，上传、创建、查询、取消任务及节点信息请求都依赖该地址。
4. **任务状态核心**：[runner.js](file:///d:/project/runninghub_api/js/runner.js) 与 [store.js](file:///d:/project/runninghub_api/js/store.js)
   - 使用单例 `currentRun`、`runningToolId` 管理任务，以工具 ID 隔离文件、参数和结果。
   - 任务经过上传、创建、轮询、取消、结果追加、自动下载和配置回填多个异步阶段。
5. **工具配置与文件一致性**：[tools.js](file:///d:/project/runninghub_api/js/tools.js)、[covers.js](file:///d:/project/runninghub_api/js/covers.js) 及 `server.py`
   - `tools/` 是权威数据源，`localStorage` 是缓存；前端和服务端都按名称或 `webappId` 去重。
   - 工具改名、删除、封面替换和重复配置清理由多个模块共同完成。
6. **DOM 渲染**：[form.js](file:///d:/project/runninghub_api/js/ui/form.js)、[results.js](file:///d:/project/runninghub_api/js/ui/results.js)、`modal.js`、`panels.js`
   - 同时存在安全 DOM 构建、转义后的 `innerHTML` 和历史结果 HTML 恢复，需要逐条追踪数据来源，不能仅凭使用 `innerHTML` 判定 XSS。
7. **安装与启动**：`installer.iss`、`启动工具.bat`、`打包安装包.bat`
   - 涉及旧进程清理、安装目录写入、资源路径、端口和重复启动，需要检查更新安装及异常退出的一致性。

上述内容只是审查入口，不代表候选问题已经成立。

## Proposed Changes

### 1. 建立审查基线和调用链

- 以当前工作区的第一方源代码为范围，不审查 `build/`、`dist/`、安装包、缓存及第三方依赖内部代码。
- 盘点 `server.py`、`launcher.py`、`index.html`、`js/**/*.js`、现有启动/打包脚本之间的入口和调用关系。
- 建立数据流清单：HTTP 参数/请求体、导入的工具 JSON、远程 API 响应、本地配置文件、用户文件路径、浏览器存储和系统对话框。
- 对每个危险操作记录对应的入口、校验、编码、授权和最终接收点。

### 2. 审查系统性 BUG

按以下跨模块主题审查，避免只报告零散表面问题：

1. **工具身份与去重规则**
   - 对比 `store.js`、`tools.js` 和 `server.py` 中按名称/`webappId` 去重的逻辑。
   - 验证同应用不同节点版本、工具改名、导入更新、缓存重置和外部删除配置文件是否会产生误删、重复或“幽灵工具”。
2. **任务生命周期与并发状态**
   - 追踪 `runner.js` 的全局运行上下文在上传、创建、轮询、取消和 `finally` 中的所有权。
   - 验证运行中切换工具、连续启动、取消与创建成功竞态、刷新页面、X 关闭后重开、彻底退出和超时路径。
   - 重点核对结果串位、重复扣费、取消状态误报、后台任务失联及自动下载遗漏。
3. **配置与封面文件一致性**
   - 检查保存、改名、去重、回收站、永久删除及封面替换的操作顺序和失败回滚。
   - 判断非原子写入、部分成功和异常中断是否会造成配置损坏、封面丢失或错误删除。
4. **异步请求与缓存可靠性**
   - 检查 HTTP 状态、JSON 结构、损坏缓存、目录扫描失败、存储容量和权限失效的处理。
   - 核对静默 `catch` 是否会把真实失败表现为成功，或让界面状态与磁盘状态长期不一致。
5. **进程与安装生命周期**
   - 核对端口占用、重复实例、托盘退出确认、启动异常、安装覆盖和旧进程清理。
   - 区分代码缺陷与既定交互设计，不把个人偏好列为 BUG。

### 3. 审查可利用安全风险

仅保留能说明攻击者输入来源、传播路径、危险接收点和现实前置条件的问题：

1. **本地 HTTP 接口边界**
   - 验证变更类接口是否接受跨站简单请求，是否校验 `Origin`、`Host`、会话标识或用户确认。
   - 重点检查文件写入/删除、系统目录操作、外部 URL 打开和关闭服务；CORS 是否能阻止请求发送与是否能阻止响应读取分别判断。
2. **服务端请求伪造**
   - 追踪 `/save-image` 的 URL 从请求体到 `urllib.request.urlopen` 的完整路径。
   - 验证任意主机、内网/环回地址、重定向及响应落盘行为；只有路径可控而主机不可控时不报告 SSRF。
3. **路径与静态文件边界**
   - 检查 `_safe_filename`、目录回退、静态文件服务、下载目录及符号链接/重解析点。
   - 通过受控样例确认是否能越出预期目录或暴露敏感文件，不把正常的绝对路径选择功能本身当作漏洞。
4. **命令与系统调用注入**
   - 检查 PowerShell 脚本拼接、目录路径插值、`subprocess`、`os.startfile` 和浏览器打开流程。
   - 必须证明攻击者能够控制进入命令或系统调用的内容；仅用户自己控制命令行参数不构成漏洞。
5. **DOM XSS 与危险 URL**
   - 对所有 `innerHTML`、`outerHTML`、动态 `href/src` 和历史结果恢复做来源到接收点追踪。
   - 验证导入配置、工具字段、远程结果、错误消息和上传预览是否已有转义与协议白名单。
6. **API Key 与敏感数据**
   - 检查请求头、查询参数、请求体、错误信息、日志、配置文件及持久化存储是否泄露 Key。
   - `localStorage` 存储是既定设计，不单独作为漏洞；只有与具体 XSS、恶意请求目标或日志暴露形成完整链路时才升级报告。

不报告纯代码风格、泛化的“缺少加固”、无可达路径的猜测、第三方依赖版本清单及单纯 DoS/资源消耗问题。

### 4. 生成修复报告

只新增 `系统性BUG与安全风险修复报告.md`，结构如下：

1. **审查范围与方法**：代码基线、覆盖文件、静态/动态验证方式及限制。
2. **执行摘要**：按严重级别统计已证实问题，说明最重要的系统性根因。
3. **系统性 BUG 清单**：编号、标题、严重级别、置信度、复现条件、影响、根因、文件/行号、修复建议、回归验证。
4. **安全风险清单**：编号、分类、标题、严重级别、数值置信度、`Source → Sink` 证据、修复建议、文件/行号。
5. **优先修复顺序**：按利用难度、数据损失、密钥暴露、重复扣费和影响范围排序，标明跨模块依赖，避免只修单点留下同类问题。
6. **已核实非问题与既定设计**：记录审查过但不成立的项目，减少后续重复误报。
7. **验证记录与剩余限制**：列出实际执行的检查、未执行的真实付费任务及无法确认的环境相关行为。

报告位置引用必须使用当前代码的准确行号和 `file:///` 链接。安全问题置信度低于 0.80、无法形成完整利用链或无法确认现实前置条件时，不进入正式问题清单；普通 BUG 也必须有确定性代码路径或可重复现象。

## Assumptions & Decisions

- 审查对象是**当前完整代码**，不是仅最近提交或差异。
- 本次“修复报告”指修复建议报告，**不直接实施修复**。
- 不读取、输出或测试真实 API Key，不提交真实 RunningHub 生成任务，不产生 API 费用。
- 动态验证仅在隔离的临时目录和测试端口进行；不修改用户工具配置、封面、下载目录或 `appinfo.txt`。
- 需要验证本地 HTTP 攻击面时，只使用无害测试负载和本地模拟服务，不访问真实内网服务。
- 不因为服务仅监听 `127.0.0.1` 就降低已证实漏洞的严重性，也不把“本地应用”视为天然安全。
- 不将 ComfyUI 项目纳入本次范围；公共核心中确认的问题会注明同步修复建议，但不同步、不修改另一个项目。

## Verification

1. 对 Python 文件执行不产生缓存的 AST 解析，对所有 JavaScript 文件执行 `node --check`，确保审查基于可解析代码。
2. 对路径清理、配置去重、任务状态转换等关键纯逻辑使用受控输入做最小验证。
3. 如需验证 HTTP 问题，在临时副本和独立端口启动服务，验证后立即停止进程并清理临时目录。
4. 对 XSS 候选使用无敏感操作的惰性测试载荷，确认是否真正执行，而非仅观察到字符串进入 HTML。
5. 对 SSRF 候选仅连接本地模拟端点，确认请求是否发出、重定向是否跟随及文件落点，不触碰真实内部服务。
6. 复核每条报告项的文件、当前行号、触发条件、影响、置信度和建议是否一致，删除重复项与推测项。
7. 最后确认业务文件和工具数据未发生变化，交付报告中明确哪些结论经过动态验证、哪些仅由确定性静态调用链证明。
